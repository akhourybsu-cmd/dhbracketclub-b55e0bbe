# Deep Claim technical protocol

Phase 0 architecture through Phase 7 deep operations and the cinematic menu/Training Journal protocol. The implementation ledger records actual verification and deployment; this protocol describes contracts rather than asserting that a migration is already live. The journal release retains snapshot schema five, field configuration seven, world generation four and production configuration four.

## Ownership and authority

Game-moment presentation is a pure consumer of confirmed state. Departure resolves a new active expedition ID from the returned snapshot, matching the requested mode, target, duration, tutorial flag and assigned crew under the same company identity and a newer revision. It is transient and not replayed from stored history. A building comparison similarly requires an actual increase between owned before/after levels. Generic saved-action recovery stays generic when those facts are unavailable.

Follow crew uses the existing public worker projection without advancing its stored stage. It focuses only a disclosed grid position or a known approach on the published route. No private terrain is generated or revealed. Active jobs past their displayed deadline still require Check return; only a server-ready DTO exposes Open haul. Receipt amounts remain the actual collection delta and staged remainder; a displayed cash total is the current company balance, not an invented earned amount. These views do not introduce database writes, new RLS policies or economic receipts.

The mobile session layer adds no economic authority. Goal refs and return-report read receipts are bounded, versioned device metadata scoped by user, club and company. Goal progress, cargo, costs and completion always come from the authorized snapshot. Initial return hydration is quiet; elapsed client timers cannot report completed work. Direct goal links validate their catalog key before opening the existing transaction review. A next-shift draft resolves a genuinely collected mining record, available crew and a currently legal public destination, then uses the unchanged server preview/revision/dispatch contract. [Session details](DEEP_CLAIM_MOBILE_LOOP.md) describe acknowledgement and UI behavior.

An authenticated member owns one company in their active club. Authentication, membership, asset installation, and onboarding belong to DH Club. `deep-claim` must be installed and enabled; private game state is never a public club leaderboard. Every backend entry point independently validates access. Changing clubs or removing membership removes access to that club's company without transferring its property.

PostgreSQL is authoritative for money, energy, assignments, terrain mutations, finite deposits, rewards and timestamps. Clients have no direct write grants to these records. Backend functions use a fixed search path, company row locks, validated references, and transactional receipts. Internal generation and reconciliation helpers have no anonymous or authenticated execution grants.

## World and version boundaries

The logical mine is 96 tiles wide, with 32×32 chunk addressing. Surface is y=0; positive y is underground. Generation expands only into needed chunks; the representation has no fixed bottom. Shaft levels support 49/99/149/299/599/999m. Phase 2 adds amethyst/gold-bearing deep seams. Phase 3 adds natural chambers, wet/crystal chambers, ruins and actual field infrastructure; the full six-region roadmap remains future content.

The company seed, unrevealed terrain, reward plans and future discoveries remain private. Global 4×3 mineral clusters cross chunk boundaries; coal follows horizontal bands and deeper geology favors iron and silver. Eight small hand-authored starter assay seams are explicitly separate from ordinary generated geology. A versioned immutable procedural base is distinct from sparse reveal, excavation and remaining-deposit mutations. Existing chunks retain their generation version. Completed expeditions and their receipts are never rerolled by a balance update.

The client receives explicitly revealed terrain only. A renderer must not reconstruct unknown tiles from a public seed or generate plausible-but-uncommitted tunnels. Fog represents missing information; it is not a second world generator.

World-generation versions and expedition rules are independent. At the Phase 2 cutover, a new chunk at chunk-y five or deeper used generation version two, while an existing version-one chunk continued to generate its unseen cells with the original algorithm. Only then-new dispatches used expedition configuration two. An in-flight version-one expedition retained its original milestones, cargo and equipment-free settlement. Later version boundaries preserve that company world/seed and existing chunk metadata.

For Phase 3, existing chunk metadata always wins. Previously absent chunks from chunk-row one/depth 32 may use generation three; chunk-row zero keeps the original geology. The new generator overlays coherent rooms on the established shallow/deep mineral distributions without changing any stored chunk or cell. Public `formation` describes an actually revealed cell, never an inferred hidden chamber. A natural empty cell becomes walkable only when revealed and connected to known excavated access. Damp chambers introduce working conditions, not an invisible impassable-water rule.

Cutover must preserve old jobs whose private plans reference chunks not yet created. The migration first obtains company/expedition write barriers in application lock order, then pins missing chunk metadata for all unapplied configuration-one/two extraction **and reveal** coordinates using the original version selector. It does not reveal those cells or edit old plans. Existing company revisions advance once to invalidate pre-migration quotes without changing their economic state. Already-committed request receipts replay before revision checks. A latest-configuration insert guard rejects cached old dispatch code with a retryable conflict after the barrier. New configuration-three dispatches pin every planned chunk before committing, preserving their geology during later expansions as well.

## Expedition transaction and reconciliation

1. Preview checks the requested crew, objective, target, duration, energy, wages, access, storage and slots without spending anything. Estimates are ranges.
2. Dispatch locks company state, validates the current configuration again, checks the idempotency fingerprint, deducts wages and each worker's energy, reserves workers, and freezes the rule/configuration snapshot and server timestamps.
3. Private deterministic milestones encode travel, preparation, work, haul and return. Only milestones whose server offsets have elapsed may be applied.
4. Reading or mutating a company lazily reconciles elapsed milestones. Offline progression does not depend on a browser timer, an online competitor or reliable cron delivery.
5. A return milestone settles exactly once, releases workers, persists the expedition log, and leaves cargo ready for collection. Three preceding work checkpoints commit cumulative ordered withdrawals, clearing one cell before excavation proceeds beyond it.
6. Collection transfers actual settled cargo in registry order exactly once per request. Partial collection leaves the remainder ready and blocks every new dispatch until resolved. Already-dispatched crews can still return, so staging is bounded by crew slots. A new partial transfer after making room is a new intentional request; retrying the previous receipt never transfers twice.

The visual system may interpolate a worker along a disclosed route or animate a pickaxe. It cannot create resource balances or excavate new cells. Closing the browser, changing local time, or returning on another device does not change the outcome.

## Phase 3 surveys, infrastructure and field events

Surveying and infrastructure use the same worker assignments, energy, wages, crew slots, private plans and elapsed milestones as mining. Both require a known, depleted, shaft-connected worksite; central-shaft cells are valid. A survey reveals only selected unknown cells within a bounded Manhattan diamond. It never withdraws ore or excavates a wall. Empty scans are rejected. Reveals occur at due work milestones. Survey and construction jobs finish directly as collected with empty cargo and a persistent field report, avoiding a meaningless empty-haul claim.

Supports, ventilation, pumps and rail consume quoted materials, construction credits, wages and energy atomically at dispatch. Duration presets correspond to project grades one/two/three. Engineering affects the frozen radius and strength. The project is visible as construction, but supplies no benefit until the crew returns. One project per cell and a base limit of 128 projects bound storage; Phase 7 raises the limit to 192 only at shaft level six. The strongest eligible support/ventilation/pump at the target reduces its corresponding incident risk. Each real route point independently chooses its strongest covering rail; averaging those strengths across the route produces the transport bonus. Separate track sections extend coverage, while overlapping sections never stack on one point. This prevents one entrance track from improving an entire deep route. Rail reduces travel and return, freeing productive time. Building an installation never changes an existing expedition's frozen plan.

Configuration-three jobs may encounter rockfall, gas or water delays. Tutorial work and sites above eight meters have zero chance. Exact depth-based conditions, safety reduction and applicable installed mitigation are quoted before dispatch. A private server-generated roll freezes one bounded setup delay, shifting work checkpoints and return together; it never destroys cargo, closes tunnels, kills workers or consumes energy twice. Extra wear is not added beyond the existing two-per-energy rule. Configurations one/two retain their original clocks and outcomes.

Quotes show base timing plus the possible delay range. Active job clocks show the true frozen schedule. A player may infer a delay from that schedule; hiding timing inference is not a security promise. Private seed/roll values are never returned. Incident type and narrative publish only at their due setup boundary. Other field reports publish only after the corresponding survey/project/find has actually occurred. Applied event receipts prevent repeat effects and duplicate report creation; rendering contributes no events.

## Recovered discoveries and permanent choices

Phase 3 introduced recovery through new configuration-three mining; current configuration-seven mining retains that rule, using a privately planned extraction cell fully depleted when the crew returns. Surveying a distant chamber does not retrieve an object through solid rock. Each company/cell can yield at most one discovery permanently. Definition, quality, detail, sale value and salvage bundle are frozen server data; reloading or repeating a request cannot reroll them. Existing depleted ground receives no retroactive find awards.

The player may keep a specimen in the company collection, sell it for its frozen value, or salvage its displayed materials. Each choice is permanent and idempotent under the company lock and request fingerprint. Salvage requires room for the complete bundle and rolls back without loss when full. Keeping supplies a real permanent collection record, not an invented DH Score or unfinished research reward. Choices have no expiration.

Twenty-four pending finds block further dispatches; already-working crews can return safely. Pending staging is bounded to 48 records. The public snapshot contains all pending finds, the latest 24 kept and latest 12 other resolved finds, plus total status counts. All history remains in the database. A full museum and paged lifetime collection remain later extensions. Public maps display recovered records only; private future finds stay inaccessible.

## Workforce and owned equipment

The server persists three hiring candidates per company/operating day, rotating through seven specialist profiles. Refreshing cannot reroll the pool. Hiring atomically checks housing, cash and the candidate's immutable identity; a hired worker retains that identity and appearance. Housing starts at three and quarters levels one/two/three increase capacity to six/nine/twelve. Existing starter workers, IDs, XP and energy are preserved. Wages are explicit worker data and apply at dispatch only.

Training costs thirty credits and raises one base statistic by up to three, capped at 100. One immutable receipt per worker/operating day enforces the limit. An assigned worker cannot train. Public worker `stats` already include level and functioning equipment bonuses; consumers must not add those bonuses again.

Each owned equipment item has an ID, frozen definition, durability, and at most one worker assignment. Slots are tool/head/utility; lanterns, cargo gear and survey instruments compete for utility. Replacing or removing gear checks that both the previous and proposed worker are idle. Dispatch freezes effective stats and item wear obligations. On completion of a configuration-two expedition, each assigned item loses two durability per energy spent exactly once. Configuration-one expeditions incur no retroactive wear. Broken items provide no bonus but never prevent basic work.

Repairs consume server-quoted credits and actual materials. Retiring an unassigned item is permanent, returns no currency or materials, and preserves its audit record. Owned non-retired gear plus uncollected crafting outputs is capped at 48. Retirement makes room without creating an equipment-resale profit loop.

## Production transaction and collection

The sixteen original versioned recipes cover four metals, quartz polishing, amethyst cutting and ten equipment items. Phase 4 adds five recipes and Phase 7 adds two, for twenty-three current recipes. A real station and its required level are mandatory. The tool station is also the equipment workshop; Deep Claim does not create another DH FORGE module. Raw minerals and refined inventory IDs are separate, and refined goods can never appear as terrain.

Starting production locks company state, validates one to ten batches, consumes all input materials and credits atomically, and freezes the recipe, equipment definition, station speed, output quantities and server timestamps. Each station has one serial timeline. Jobs whose start is in the future remain `active` in storage but display as queued. A company can have at most three uncollected production jobs across stations. Upgrading a station shortens future jobs only.

Authorized reads/mutations reconcile elapsed jobs to ready exactly once. A client countdown cannot mint outputs. Material collection uses real warehouse space and leaves overflow staged, with later intentional partial transfers using new receipts. Equipment is instantiated once on collection. Both the job status and request receipt prevent duplicate outputs, including a retry with a lost acknowledgement. Any ready mining haul or production job must be collected before another mining dispatch; ready production also occupies its queue slot until resolved. Starting more work cannot evade the three-job or equipment-cap limits. There is no automatic production loop, NPC input purchase, or cancellation refund.

## Company development and frozen industry

Schema four adds one company development catalog and owned business state. Seven research branches contain fourteen once-only upgrades with explicit prerequisites, real credit/material costs and Research Office requirements. A company can fund one research order at a time. Its definition, inputs, charge and server timestamps are frozen at purchase. Completion reconciles under the same company lock; it needs no collection click and cannot be accelerated by a device clock. There is no cancellation refund or repeatable research-income source.

Completed research contributes bounded company-wide bonuses to the effective employee statistics used for new quotes and dispatches, capped at 100 after existing levels, training and gear. Base statistics remain distinct. Research bonuses are exposed separately for explanation and must never be added twice to public effective stats. Phase 4 retained expedition configuration three: research changed its already-frozen crew inputs without replacing the terrain/field algorithm. Phase 7 uses configuration seven for new field operations while preserving earlier plans, equipment snapshots, incidents, energy charges, cargo and return clocks.

Processing research reduces newly queued production times by five percent and then an additional ten percent. Apply integer ceiling after the station modifier, with a twenty-second minimum; store the actual modifier and effective duration with the job. Already queued or staged production keeps its original recipe, costs, outputs and clocks. Five new version-one recipe keys add bronze, steel, gold and two steel equipment items. The sixteen original recipe definitions and ten original gear definitions remain immutable. New recipes enforce research on the backend; the UI can explain a lock but cannot unlock it.

The Trading Post exposes twelve finite company delivery contracts in three prerequisite tiers. Orders are persistent and have no expiration, reroll or separate acceptance step. Fulfillment consumes the complete frozen requirement from collected warehouse stock and grants the frozen company-credit payout atomically. Staged cargo, uncollected production and undecided finds are not inventory. One company/key record prevents a second delivery; request receipts recover a lost acknowledgement without another withdrawal or payout. No contract grants equipment, energy or DH Score.

Eight company milestones use durable completed expeditions, collected production, completed research, installed projects, kept discoveries and deliveries. Progress is calculated from source records, including eligible historical activity. Only explicit secured claims grant the finite credit award; clients cannot submit progress, eligibility or reward amounts. Once-only claim records and company locks prevent duplicate awards. These company-credit objectives remain separate from the existing-ledger DH Feats integration introduced in Phase 5.

Operational totals aggregate authoritative records across the company history, not just the recent public log. Collected processing quantities use frozen recipe outputs multiplied by batches, because a job's mutable output field represents the remaining staged stock. Survey totals use actual applied revelations. A zero-cargo expedition, preview, repeatedly read result or duplicate receipt cannot be treated as new processed goods or delivered stock.

Research Office and Trading Post upgrades have actual research/contract-tier functions. They reuse the existing building purchase, reserve and visual ownership model. The six-tab game shell remains; the company office provides compact Company, Research, Contracts and Records views instead of another global navigation system.

## Optional club participation

Phase 5 retained private snapshot schema four when it introduced the separate version-one club projection; that projection remains separate from the current schema-five private snapshot. It contains only current-club public records, the caller's sharing choices, finite project progress and sanitized showcase items. It never returns another company's wallet, inventory, employees, mine, coordinates, active jobs, plans or private company ID. Club reads are lazy, bounded and independently recoverable; their failure does not disable private mining. Account/club/metric/page query keys isolate cached views. `own_revision` prompts a private refresh after club reconciliation before another reviewed spend.

Shared entry points reuse membership and installed-asset checks and additionally require the existing registry-backed `dh_public_member`. The self-visible private-account helper is insufficient for collective play. Every displayed company belongs to a current public member of the same eligible club. Standings and showcases have independent consent flags, both initially false. Opting out removes server projections without refunding contributions or erasing progress. Showcase selection validates up to three owned, permanently kept finds. Only kind, name, quality and detail are published. Own retained IDs and parallel sanitized details let an older selected find remain editable after it leaves the recent private cabinet list.

Three distinct standings avoid a synthetic combined score. Weekly mining value prices original frozen cargo from recorded returned mining/exploration jobs; staged remainders and later sales cannot change it. The ten mineral prices shipped through field rules three are immutable valuation inputs. Depth is the greatest completed mining target. Best find is the highest recovered, frozen specimen value. Ties share a rank, identities remain unique, and a caller outside the top fifty receives one additional row. Club-local Monday boundaries use validated IANA timezones; calendar dates, including daylight-saving changes, define the week. Reading shared standings never reconciles or locks other companies. Returns appear after their company records them.

Six authored projects form a finite prerequisite chain. Only an open project gets a frozen club row; its goals, unit prices, total value, credit pool and initial membership cap are preserved. One/two/three-or-more public club members freeze a per-resource cap of 100/60/40 percent. The effective cap can increase if membership shrinks, and never falls below its frozen floor. New members do not invalidate earlier donations. Contributions may be made without listing the company publicly.

A contribution locks authorization/asset records, the caller's company and then the project. It validates every positive whole quantity against collected stock, global remaining goals and the caller's per-resource limit. The whole action rejects on any failure; quantities are never silently clipped. After debits, cash plus remaining collected saleable stock must retain two operating credits. Pending cargo, equipment, finds and unclaimed rewards cannot satisfy that reserve. Immutable contribution rows and the existing request fingerprint commit together with project progress. No other company is locked or credited while holding the shared project.

Actual contribution value must reach five percent of the frozen total to qualify. When complete, the caller may claim `floor(reward_pool × own_value / total_value)` once. The six authored pools total 3,771 credits against 12,572 of contributed material value; integer shares cannot exceed a pool. Claim receipts remain separate from dismissible UI and survive retries, opt-out and club departure. A returning eligible member may recover an unclaimed legitimate share. Contributions themselves are permanent, with no refunds, player trading, recurring resets or resource rewards. Former or private member identities are omitted while committed material totals persist.

The six main tabs remain. Club Projects, Standings and Showcase live inside the Company Office. Notification query links are whitelisted after authentication, membership and asset checks. A notice for another active club never switches identity or opens that club's private state.

## DH Feats and shared inbox

Seven Deep Claim families extend the existing DH Feats catalog, metric collector, dirty-account queue and permanent award receipts. Thirty-two tier unlocks total 590 DH points; company credits remain separate. Metrics count returned mining shifts, completed depth, fully collected processed units, completed research, delivered orders, installed infrastructure and qualified participation in completed club projects. Previewing, dispatching, pending stock, contribution clicks and reward-claim clicks do not add achievements.

Eligible lifetime source history includes the account's legitimate past companies after club changes or source-app removal. Registry-hidden accounts/workspaces remain excluded. Sharing consent controls public company projections, not earned account achievements. Only the new families receive historical import; imported awards are excluded from monthly totals and reveals. Existing catalog entries, point snapshots, earned timestamps and account preferences are preserved. Real post-integration completions can contribute UTC activity dates and feature variety without retroactively inventing general engagement. Company-owned source triggers resolve the owner ID before marking that existing account dirty. Shared project completion skips busy account locks; the existing collector's reconciliation repairs missed invalidation.

In-app notifications use the existing inbox and its `deep_claim` preference. Private event receipts deduplicate meaningful crew returns, ready production, research, major finds and completed projects independently of inbox dismissal. Reconciliation batches a summary with a fifteen-minute cooldown and at most four messages per local operating day. Preference changes suppress pending/off-period history rather than flooding on re-enable. Historical migration activity is suppressed without changing Feat history. Project notices are queued only during each contributor's later own reconciliation, avoiding foreign-company FK locks while the project is held.

Notifications require current public membership and an enabled visible installation, even though lifetime Feats retain earlier legitimate activity. Loading and preference writes have timeout, identity and rollback protection; a failed preference save does not claim success or overwrite other preferences. Delivery uses lazy server reconciliation and the existing inbox refresh/subscription. Unattended scheduling and device push are not claimed.

## Energy and operating calendar

Each worker starts with six energy per operating day. Quick/Standard/Deep shifts cost one/two/three energy for every assigned worker and last 20/60/180 minutes. The one-time induction run is accelerated on the server. The server validates `clubs.settings.timezone` against PostgreSQL IANA names, using America/New_York when absent or invalid. The company persists its next UTC reset boundary; zone changes are adopted at the next reset, rather than granting repeated energy immediately. Timestamps remain UTC and database timezone conversion handles 23/25-hour daylight-saving days. Offline days never accumulate more than six energy.

## Retry, isolation and client behavior

Every economic mutation carries a UUID request identity and a validated argument fingerprint. Reusing the identity with different arguments is rejected. Retrying a committed request restores authorized current state without spending or awarding again. Company locking serializes conflicting device actions; independent companies do not share a lock.

React Query keys include account and club. Responses carry a company revision; an older response cannot replace newer state. Pending mutation identities survive interrupted requests, are account/club scoped, and are never silently replayed as a new purchase. Loading uses the shared timeout guard and exposes a retry. Cached data is informational while disconnected; purchases, dispatches and collection require server confirmation.

## Ancient Deep version seven

The additive expansion introduces field configuration seven, world generation four and public snapshot schema five. Production configuration four is retained because queue, station, research, payment, duration and item-freeze rules do not change. Schema five adds canonical `deep_catalog` seven and a bounded `deep_operations` summary; field catalog three, business catalog four and club catalog five remain exact. Older snapshots remain valid. The twenty-five member RPC signatures and argument fingerprints stay stable.

Shaft six costs 24,000 credits and requires completed `deep_operations_2`, whose original ingredients are all obtainable above the former depth cap. Actual shaft access extends to 999 metres, with a constructed centreline through 956. A seventy-five-percent lift discount is weighted by actual eligible route-edge length divided by the whole Manhattan route. Each vertical centreline edge needs both endpoints known and excavated inside that corridor. Compressed segments are expanded logically and clipped; a missing underground cell or side branch cannot receive a lift benefit. The built shaft guarantees its public surface landing at (48,0), which the underground tile DTO intentionally omits; only that surface point can be inferred by the visual helper. Apply integer ceiling to lift travel, then the original weighted-rail reduction and twenty-second stage floor. New jobs freeze these values before spending. Existing jobs retain their original travel even if a lift is bought later.

Mining and exploration at depth 600 or greater use heat load `min(40,30+2*floor((depth-600)/100))`. Subtract effective average Engineering divided by ten and floored, the strongest installed covering ventilation strength, and average working assigned gear protection floored and capped at fifteen. Remaining penalty is at least zero. Extraction uses `floor(raw_work_seconds*(100-penalty)/100)` once.
